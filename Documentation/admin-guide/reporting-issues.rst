报告问题
++++++++


简明指南(即 TL;DR)
====================

你是否在使用同一 stable 或 longterm 系列的原版(vanilla)内核时遇到了回归(regression)?该系列是否仍在支持期内?如果是,请先在 `LKML <https://lore.kernel.org/lkml/>`_ 和 `Linux stable 邮件列表 <https://lore.kernel.org/stable/>`_ 的存档中搜索是否有可以加入的同类报告。如果找不到,请安装`该系列的最新版本 <https://kernel.org/>`_。如果问题仍然出现,请向 stable 邮件列表(stable@vger.kernel.org)报告,并抄送(CC)回归问题列表(regressions@lists.linux.dev);最好同时抄送相关子系统的维护者及其邮件列表。

对于其他所有情况,请尽力推测可能是内核的哪个部分引发了问题。查看 :ref:`MAINTAINERS <maintainers>` 文件,了解该部分的开发者希望以何种方式获知问题——大多数情况下是通过电子邮件,并抄送相应的邮件列表。查看目标渠道的存档中是否有同类报告;同时也请在 `LKML <https://lore.kernel.org/lkml/>`_ 和网络上搜索。如果找不到可以加入的讨论,请安装`最新的 mainline 内核 <https://kernel.org/>`_。如果问题在该版本上依然存在,就发送一份报告。

问题在那里已被修复,但你希望它在仍在支持期内的 stable 或 longterm 系列中也得到解决?那么请安装该系列的最新版本。如果问题依然存在,请在 mainline 中找到修复该问题的改动,并检查其回迁(backport)是否正在进行或已被放弃;如果两者都不是,请向处理该改动的人提出请求。

**一般说明**:按照上述方式安装和测试内核时,请确保它是原版(vanilla)内核(即:未经修补,且未使用附加模块)。同时确保它构建并运行在健康的环境中,并且在问题发生之前尚未被污染(tainted)。

如果你在 Linux 内核上同时遇到多个问题,请逐个分别报告。撰写报告时,请包含与问题相关的所有信息,例如所用的内核和发行版。如果是回归,请在报告中抄送回归问题邮件列表(regressions@lists.linux.dev)。另外,请尝试通过二分(bisection)定位引入问题的提交;如果成功,请在报告中附上其 commit-id,并抄送 sign-off 链中的所有人。

报告发出后,请回答随之出现的各种问题,并在能力范围内提供协助。这包括通过不时地用更新的版本重新测试来推动进展,并在测试后发送状态更新。

向内核维护者报告问题的分步指南
==============================

上面的 TL;DR 大致说明了如何向 Linux 内核开发者报告问题。对于已经熟悉向自由/开源软件(FLOSS)项目报告问题的人来说,这些内容可能已经够用了。对于其他人,则有本节。本节更加详细,采用分步的方式进行。出于可读性的考虑,它仍力求简洁,省略了大量细节;这些细节将在分步指南下方的参考章节中描述,其中会对每个步骤做更详细的解释。

注意:本节涵盖的内容比 TL;DR 略多一些,处理顺序也稍有不同。这是为了你好:确保你能及早发现一个看似 Linux 内核问题的故障,实际上是否由别的原因造成。因此,这些步骤有助于确保你在此过程中投入的时间最终不会白费:

 * 你遇到的问题是否出现在硬件或软件厂商提供的 Linux 内核上?那么在几乎所有情况下,你最好停止阅读本文档,转而向你的厂商报告问题——除非你愿意自行安装最新的 Linux 版本。要知道,追查并修复问题时往往终究需要这样做。

 * 用你顺手的互联网搜索引擎粗略搜索已有的报告;此外,请查看 `Linux 内核邮件列表(LKML) <https://lore.kernel.org/lkml/>`_ 的存档。如果找到匹配的报告,请加入讨论,而不要另发新报告。

 * 看看你正在处理的问题是否属于回归(regression)、安全问题或极其严重的问题:它们属于"高优先级问题",在接下来的某些步骤中需要特殊处理。

 * 确保你面临的问题不是内核周边环境造成的。

 * 创建一份全新的备份,并把系统修复与恢复工具放在手边。

 * 确保你的系统没有在动态构建额外的内核模块来增强内核——DKMS 之类的方案可能会在本地悄悄做这件事。

 * 检查问题发生时你的内核是否已被"污染"(tainted),因为导致内核设置该标志的事件可能正是造成你所面临问题的原因。

 * 粗略写下如何复现该问题。如果你同时处理多个问题,请为每个问题分别建立笔记,并确保它们在一台新启动的系统上能够独立复现。这一步是必需的,因为每个问题都需要单独向内核开发者报告,除非它们紧密交织在一起。

 * 如果你遇到的是 stable 或 longterm 版本线内的回归(比如从 5.10.4 更新到 5.10.5 时某些功能坏了),请向下翻到"处理 stable 和 longterm 内核版本线内的回归"。

 * 定位疑似引发该问题的驱动程序或内核子系统。查明其开发者希望在何处、以何种方式接收报告。注意:大多数情况下这并不是 bugzilla.kernel.org,因为问题通常需要通过邮件发送给维护者和公开邮件列表。

 * 在相关 bug 跟踪器或邮件列表的存档中彻底搜索可能与你的问题匹配的报告。如果找到任何内容,请加入讨论,而不要另发新报告。

完成这些准备工作后,现在进入主体部分:

 * 除非你已经在运行最新的"mainline" Linux 内核,否则最好为报告流程安装它。在某些情况下,用最新的"stable" Linux 进行测试和报告也是可以接受的替代方案;在合并窗口(merge window)期间,这样做实际上可能反而是最佳选择,但在这个开发阶段,先暂停几天再继续往往是更好的主意。无论选择哪个版本,理想情况下都请使用"vanilla"构建。忽视上述任何一条建议,都会大幅增加你的报告被拒绝或被无视的风险。

 * 确保你刚安装的内核在运行时不会自行"污染"(taint)。

 * 用刚安装的内核复现该问题。如果问题没有出现,请向下翻到针对"仅发生在 stable 和 longterm 内核上的问题"的说明。

 * 优化你的笔记:设法找到并写下复现问题的最直接方法。确保最终结果包含所有重要细节,同时又便于初次接触该问题的人阅读和理解。如果你在此过程中有新的发现,请考虑重新搜索关于该问题的已有报告。

 * 如果你的故障涉及"panic"、"Oops"、"warning"或"BUG",请考虑解码内核日志,找到触发错误的代码行。

 * 如果你的问题是回归,请尽可能缩小该问题被引入的时间范围。

 * 开始撰写报告:先写下关于问题的详细描述。有几项内容必须始终提及:你为复现问题而安装的最新内核版本、所使用的 Linux 发行版,以及你关于如何复现问题的笔记。理想情况下,请将内核的构建配置(.config)和 ``dmesg`` 的输出放到网络上某个可访问的地方并附上链接。包含或上传所有其他可能相关的信息,例如 Oops 的输出/截图或 ``lspci`` 的输出。写完这个主体部分后,在其上方插入一段正常长度的段落,快速概述问题及其影响。再在这之上加一句话,简短描述问题,吸引人们读下去。然后给它起一个描述性的标题或主题,还要比之前更简短。接下来,你就可以按照 MAINTAINERS 文件的指引发送或提交报告了——除非你面对的是前述"高优先级问题"之一:它们需要特殊处理,参见下文"高优先级问题的特殊处理"。

 * 等待反馈,并推动事情持续进展,直到你能以某种方式接受结果为止。因此,请公开且及时地回应任何询问。测试他人提出的修复方案。进行主动测试:至少在每个新 mainline 版本的第一个候选版本(RC)发布时重新测试并报告结果。如果事情陷入停滞,发送友好的提醒。如果没有得到任何帮助,或结果不尽如人意,也请尽力自救。


报告 stable 和 longterm 内核版本线内的回归
------------------------------------------

本小节适用于这种情况:你按照上述流程操作,并在"stable 或 longterm 内核版本线内的回归"这一步被指引到这里。如果从 5.10.4 更新到 5.10.5 时某些功能坏了,你面对的就是这类回归(从 5.9.15 切换到 5.10.5 则不算)。开发者希望尽快修复这类回归,因此为报告它们提供了一个精简流程:

 * 检查内核开发者是否仍在维护你关心的 Linux 内核版本线:前往 `kernel.org 首页 <https://kernel.org/>`_,确认页面上在提及该版本线的最新发布时未带"[EOL]"标记。

 * 查看 `Linux stable 邮件列表 <https://lore.kernel.org/stable/>`_ 的存档中是否已有相关报告。

 * 将该版本线的最新发布安装为原版(vanilla)内核。确保该内核未被污染且仍能复现问题,因为问题可能已在其中被修复。如果你最初是在厂商内核上发现问题的,也请检查最后一个已知正常版本的原版构建是否同样运行良好。

 * 向 Linux stable 邮件列表(stable@vger.kernel.org)发送一份简短的问题报告,并抄送 Linux 回归邮件列表(regressions@lists.linux.dev);如果你怀疑原因出在某个特定子系统,请同时抄送其维护者及其邮件列表。大致描述该问题,最好说明复现方法。提及出现问题的第一个版本以及最后一个正常的版本。然后等待进一步的指示。
