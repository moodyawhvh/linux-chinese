========
CVE 编号
========

通用漏洞披露（Common Vulnerabilities and Exposures，CVE®）编号最初被设计为一种无歧义地识别、定义和编目公开披露的安全漏洞的方式。随着时间的推移，其对内核项目而言的作用已逐渐下降，而且 CVE 编号经常以不恰当的方式、出于不恰当的理由被分配。正因如此，内核开发社区一直倾向于回避它们。然而，持续存在的分配 CVE 及其他形式安全标识符的压力，加上内核社区之外的个人和公司对其不断的滥用，清楚地表明：内核社区应当掌控这些编号的分配。

Linux 内核开发团队确实有能力为潜在的 Linux 内核安全问题分配 CVE。该分配过程独立于 :doc:`常规的 Linux 内核安全缺陷报告流程<../process/security-bugs>`。

Linux 内核所有已分配 CVE 的列表可以在 linux-cve 邮件列表的存档中找到，见 https://lore.kernel.org/linux-cve-announce/ 。若想及时获知新分配的 CVE，请`订阅 <https://subspace.kernel.org/subscribing.html>`_ 该邮件列表。

流程
====

作为常规稳定版（stable）发布流程的一部分，负责 CVE 编号分配的开发者会识别出可能属于安全问题的内核改动，并为它们自动分配 CVE 编号。这些分配结果会经常性地以公告形式发布在 linux-cve-announce 邮件列表上。

注意，由于 Linux 内核在系统中所处的层次，几乎任何缺陷（bug）都可能被利用来危害内核安全，而在缺陷被修复时，其可利用性往往并不明显。正因如此，CVE 分配团队采取了格外谨慎的态度，为他们识别出的每一个缺陷修复（bugfix）都分配 CVE 编号。这也解释了 Linux 内核团队发布的 CVE 数量为何看起来如此之多。

如果 CVE 分配团队遗漏了某个你认为应当分配 CVE 的具体修复，请发送邮件至 <cve@kernel.org>，那里的团队会与你一同处理。注意，不要向这个邮件别名发送任何潜在安全问题，它仅用于为已进入已发布内核树的修复分配 CVE。如果你认为自己发现了一个尚未修复的安全问题，请遵循 :doc:`常规的 Linux 内核安全缺陷报告流程<../process/security-bugs>`。

对于 Linux 内核中尚未修复的安全问题，不会自动分配 CVE；只有当修复可用并已应用到某个稳定内核树之后，才会自动进行分配，并通过原始修复的 git commit id 加以跟踪。如果有人希望在问题通过提交解决之前就获得 CVE 分配，请联系内核 CVE 分配团队 <cve@kernel.org>，从他们预留的标识符批次中获取一个标识符。

对于 Stable/LTS 内核团队当前不再积极维护的内核版本中发现的任何问题，都不会分配 CVE。当前受支持的内核分支列表见 https://kernel.org/releases.html

对已分配 CVE 的异议
===================

对与特定内核改动相关的已分配 CVE 提出异议或加以修改的权力，仅属于受影响的相关子系统的 maintainer（维护者）。这一原则确保了漏洞报告的高度准确性与可问责性。只有对该子系统具备深厚专业知识和透彻了解的人，才能有效评估所报告漏洞的真实性与影响范围，并确定其恰当的 CVE 定性。任何在这一指定权限之外修改或质疑 CVE 的行为，都可能造成混乱和不准确的报告，并最终导致系统被攻破。

无效的 CVE
==========

如果某个安全问题仅存在于由某个 Linux 发行版支持的 Linux 内核中——原因在于该发行版自身所做的改动，或该发行版所支持的内核版本已不再是 kernel.org 支持的版本之一——那么 Linux 内核 CVE 团队无法为其分配 CVE，必须向该 Linux 发行版本身申请。

对于处于积极支持状态的内核版本，任何由内核 CVE 分配团队之外的组织针对 Linux 内核分配的 CVE，都不应被视为有效 CVE。请通知内核 CVE 分配团队 <cve@kernel.org>，以便他们通过 CNA 补救流程使这些条目失效。

特定 CVE 的适用性
=================

由于 Linux 内核可以以许多不同的方式使用，外部用户可以通过许多不同的途径访问它，也可能根本无法访问，因此任何特定 CVE 的适用性都由 Linux 用户自行判断，而非由 CVE 分配团队决定。请不要联系我们试图确定某个特定 CVE 的适用性。

此外，由于源码树非常庞大，而任何一套系统只会使用源码树中的一小部分，所有 Linux 用户都应当意识到，大量已分配的 CVE 与他们的系统并不相关。

简而言之，我们不了解你的使用场景，也不知道你使用了内核的哪些部分，因此我们无从判断某个特定 CVE 是否与你的系统相关。

与以往一样，最好的做法是采纳所有已发布的内核改动，因为它们是由众多社区成员作为一个统一的整体共同测试过的，而不是逐个挑选（cherry-pick）的零散改动。另请注意，对于许多缺陷而言，整个问题的解决方案并非存在于单个改动之中，而是由多个相互叠加的修复共同构成的。理想情况下，所有问题的所有修复都会被分配 CVE，但有时我们也会有疏漏，因此请假定某些未分配 CVE 的改动可能同样值得采纳。
