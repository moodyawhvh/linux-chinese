安全缺陷
========

Linux 内核开发者非常重视安全问题。因此,一旦发现安全缺陷(security bug),我们希望能尽快得知,以便尽早修复并披露。

准备报告
--------

与任何缺陷报告一样,一份安全缺陷报告需要开发者投入大量的分析工作,因此你所能提供的关于问题的信息越多越好。如果你不清楚哪些信息是有帮助的,请先查阅 Documentation/admin-guide/reporting-issues.rst 中所述的流程。**任何**一份安全缺陷报告中,以下信息都是绝对必需的:

  * **受影响的内核版本范围**:若不注明版本,你的报告将不会被处理。请注意,"最新 mainline"这类依赖时间的版本表述是不可接受的,必须提供稳定的标识符,例如 commit ID 或确切的版本号。非来自 kernel.org 的内核版本(例如发行版内核)对维护者来说毫无意义,报告同样不会被处理。相当一部分报告所涉及的缺陷其实早已被修复,因此极其重要的一点是:必须在较新的版本(开发树或最新稳定版)上验证漏洞,至少要确认自发现该问题的版本以来相关代码未被改动。

  * **问题的描述**:需要对问题进行详细描述,附上展现其表现的跟踪信息(trace),并说明为什么你认为所观察到的行为属于内核中的问题。

  * **复现程序(reproducer)**:开发者必须能够复现问题,才会认为某项修复是有效的。这既包括触发问题的方式,也包括确认问题确实发生的方式。复现程序应当少依赖复杂环境(源代码、shell 脚本、指令序列、文件系统镜像等)。不接受仅含二进制的可执行文件。可用的 exploit(漏洞利用程序)极有帮助,未经报告者同意不会对外发布,除非其已经公开。从定义上讲,一个问题如果无法复现,那么它就不可利用,因而也就不是安全缺陷。

  * **触发条件**:如果该缺陷依赖于特定的配置选项、sysctl、权限、时序、代码修改等,应当予以说明。

此外,以下信息也非常有价值:

  * **疑似缺陷位置**:疑似存在缺陷的文件名和函数非常重要,至少有助于把报告转交给相应的维护者。当无法给出时(例如"每当我运行这个命令,系统就死机"),安全团队会协助定位缺陷来源。

  * **建议的修复**:分析过源代码中缺陷成因的报告者,几乎总是对如何修复有准确的思路,因为他们花了很长时间研究该问题及其影响。提出一个经过测试的修复会为维护者节省大量时间,即使该修复最终并非正确方案,也有助于理解这个缺陷。提出经过测试的修复时,请务必将其格式化为可直接合并的形式(参见 Documentation/process/submitting-patches.rst)。这样一旦被接受,可以省去一些来回沟通,而且你也会因发现并修复该问题而获得署名。注意,在这种情况下,当报告者与补丁作者为同一人时,只需要一个 ``Signed-off-by:`` 标签,而无需 ``Reported-by:``。

  * **缓解措施**:在缺陷分析过程中,常常会出现一些缓解该问题的办法。分享这些办法很有用,因为它们可以在最终用户获得修复之前的这段时间内为其提供保护。

何为安全缺陷
------------

大多数缺陷应当公开处理,以便让尽可能广泛的人群参与进来并找到最佳解决方案,这一点很重要。本质上,在小范围参与者之间私下讨论处理的缺陷,更难产生最佳的修复(例如,可能遗漏有效的使用场景,测试能力也有限)。

事实证明,通过安全团队报告的缺陷中,大多数其实只是普通缺陷,只是由于不了解 Linux 内核的威胁模型(threat model,参见 Documentation/process/threat-model.rst)而被错误地归类为安全缺陷,它们本应按照 Documentation/admin-guide/reporting-issues.rst 中描述的正常渠道提交。

安全邮件列表用于那些紧急缺陷:它们使攻击者在配置正确的生产系统上获得本不应拥有的能力,并且容易被利用,对众多用户构成迫在眉睫的威胁。报告之前,请考虑该问题在这样的系统上是否真的跨越了信任边界(trust boundary)。

**如果你借助了 AI 辅助来发现缺陷,就必须将其视为已公开**。尽管你可能有充分的理由认为它并未公开,但安全团队的经验表明,以这种方式发现的缺陷几乎总会同时出现在多名研究者面前,而且往往是在同一天。在这种情况下,请不要公开分享复现程序,以免造成意外的危害;只需说明你手头有复现程序即可,维护者如有需要会私下向你索取。

如果你不确定某个问题是否符合标准,宁可私下报告:安全团队宁愿多分诊一份处于边缘的报告,也不愿漏掉一个真实的漏洞。不过,把普通缺陷报告到安全列表并不会使其得到更快的处理,反而会消耗其他报告所需的分诊能力。

确定联系对象
------------

报告安全缺陷最有效的方式,是将其直接发送给受影响子系统的维护者,并抄送(Cc:)Linux 内核安全团队。在此阶段不要发送到公开邮件列表,除非你有充分的理由认为该问题已经公开、或者很容易被发现(例如,问题出自人人可复现的、广泛可得的自动化漏洞扫描工具,或者出自基于 AI 的工具)。

如果你要报告的问题影响内核中的多个部分,即使这些问题相当相似,也请分别单独发送邮件(要考虑到维护者不会同时在处理这些问题)。唯一的例外是:当问题涉及由完全相同的一组维护者维护的紧密相关部分,并且这些部分预计将通过同一个 commit 一次性修复时,一次性报告它们是可以接受的。

对大多数首次报告者而言,一个难点是确定该把报告发送给哪些收件人。在 Linux 内核社区,所有官方维护者都是可信的,因此不小心将错误的维护者列入收件人,后果基本上只是给对方增添一点噪音,并无大碍。因此,确定维护者列表的一个合适方法(内核安全官员也在使用)是借助 get_maintainer.pl 脚本,并将其调整为只输出维护者。该脚本在给定文件名时,会在 MAINTAINERS 文件中查找其路径,从而得出相关维护者的层级列表。首次以最细粒度的过滤条件调用它时,大多数情况下会返回该文件维护者的一个简短列表::

  $ ./scripts/get_maintainer.pl --no-l --no-r --pattern-depth 1 \
    drivers/example.c
  Developer One <dev1@example.com> (maintainer:example driver)
  Developer Two <dev2@example.org> (maintainer:example driver)

随后应将邮件发给这两位维护者。如果该命令没有返回任何结果,说明受影响的文件属于一个更大的子系统,此时应放宽过滤条件::

  $ ./scripts/get_maintainer.pl --no-l --no-r drivers/example.c
  Developer One <dev1@example.com> (maintainer:example subsystem)
  Developer Two <dev2@example.org> (maintainer:example subsystem)
  Developer Three <dev3@example.com> (maintainer:example subsystem [GENERAL])
  Developer Four <dev4@example.org> (maintainer:example subsystem [GENERAL])

这里选择前几位最具体的维护者就足够了。当列表很长时,可以用如下命令生成一行以逗号分隔的电子邮件地址列表,方便填入邮件客户端的 To: 字段::

  $ ./scripts/get_maintainer.pl --no-tree --no-l --no-r --no-n --m \
    --no-git-fallback --no-substatus --no-rolestats --no-multiline \
    --pattern-depth 1 drivers/example.c
  dev1@example.com, dev2@example.org

或者用下面这条命令生成更宽泛的列表::

  $ ./scripts/get_maintainer.pl --no-tree --no-l --no-r --no-n --m \
    --no-git-fallback --no-substatus --no-rolestats --no-multiline \
    drivers/example.c
  dev1@example.com, dev2@example.org, dev3@example.com, dev4@example.org

如果到这里你仍然难以找到正确的维护者,**且仅在这种情况下**,才可以只把报告发送给 Linux 内核安全团队。你的邮件会被分诊,如有需要,你会收到关于应当联系谁的指引。你的邮件也可能被原样转发给相关维护者。
